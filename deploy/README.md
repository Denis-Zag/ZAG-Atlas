# Установка ZAG Atlas на Linux-сервер

**Полный серверный запуск с настоящим доменом и HTTPS пока не проверен.** Проверки скрипта и конфигурации описаны в [результатах](../verification/INSTALLER_RESULTS.md). Срок установки не обещается.

## Короткий путь

Заранее подготовьте Linux-сервер с Docker Engine и Compose 2.30 или новее. Направьте домен на этот сервер; TCP-порты 80 и 443 должны быть свободны и доступны извне. Получите ключ ProxyAPI.

1. Скопируйте весь проект на сервер и откройте его папку в терминале сервера. Здесь должны находиться install.sh, Dockerfile, compose.server.yaml и папка deploy. На Windows можно подключиться к серверу по SSH и выполнять команды уже там.
2. Выполните:

   ```bash
   bash install.sh
   ```

3. Введите домен без `https://`, пути и порта, например `atlas.company.ru`. Затем введите ключ ProxyAPI без обрамляющих кавычек и первоначальный пароль admin длиной 8–128 символов. Повторите пароль. Ключ и пароль не отображаются при вводе.
4. После успешной проверки откройте выданный HTTPS-адрес с компьютера сотрудника. Войдите как admin, обязательно смените пароль, заполните название и описание компании, загрузите документы и создайте сотрудников.

Установщик запускает приложение, Qdrant и Caddy. Caddy запрашивает и обновляет сертификат и перенаправляет HTTP на HTTPS. На компьютерах сотрудников достаточно браузера. Отдельная программа-распаковщик или установщик для сотрудников не нужна.

## Что требуется до запуска

| Требование | Как проверить |
|---|---|
| Linux и Bash | Скрипт предназначен для терминала VPS, а не локального PowerShell |
| Доступ к локальному Docker Engine | `docker info`; удалённый Docker-контекст установщик отклоняет |
| Compose 2.30 или новее | `docker compose version`; версия нужна для передачи секретов без изменения спецсимволов |
| Базовые команды сервера | curl, getent, ss, mktemp; для обычного Debian/Ubuntu ss входит в iproute2 |
| DNS домена | Записи A и, если используется, AAAA указывают на этот сервер; кириллическое имя вводится в Punycode |
| Внешний доступ | Порты 80/443 свободны на сервере и разрешены сетевыми правилами провайдера/сервера |
| Исходящие соединения | Сборка загружает образы и пакеты; Caddy обращается к центру сертификации, приложение — к ProxyAPI |
| Диск и память | Место для образов, документов, векторов и копий; память для приложения, OCR и Qdrant. Один Qdrant ограничен 1 ГиБ и одним CPU; это не минимум ресурсов всего сервера |

Docker и сетевые правила скрипт самостоятельно не устанавливает и не изменяет. Подготовку сервера выполняет его администратор. [Установка Docker](https://docs.docker.com/engine/install/) и [плагина Compose](https://docs.docker.com/compose/install/linux/).

Проверка основных требований без создания настроек и запуска сервисов:

```bash
bash install.sh --check
```

Этот режим проверяет комплект, Docker и локальные порты. DNS, сертификат, модель и приложение им не проверяются.

## Что создаётся и сохраняется

| Файл или ресурс | Назначение |
|---|---|
| .env.server | Серверные настройки, ключ ProxyAPI и первоначальный пароль; файл создаётся с правами 600 |
| deploy/server-domain.env | Только домен для подстановки в серверный Compose |
| compose.server.yaml | Отдельный серверный профиль, не накладываемый на локальный compose.yaml |
| deploy/Caddyfile | Готовая конфигурация HTTPS-прокси; домен подставляется при запуске |
| Проект zag-atlas-server | Отдельные контейнеры, сеть и именованные тома |
| atlas-data и qdrant-data этого проекта | База компании и индекс |
| caddy-data и caddy-config этого проекта | Сертификаты и данные HTTPS-прокси |

Локальные compose.yaml, .env и тома проекта zag-atlas установщик не меняет. Серверные файлы настроек исключены из Git и контекста сборки. Копировать .env.server в публичный архив не нужно.

При повторном `bash install.sh` существующий .env.server используется без перезаписи и без повторного запроса ключа/пароля. Если есть серверные тома, но нет их файла настроек, установка останавливается: нужно восстановить исходный .env.server. Изменение ADMIN_PASSWORD не сбрасывает пароль уже созданной учётной записи; сброс сотрудников выполняет администратор через сайт.

Секреты передаются приложению через `env_file` с `format: raw`: `$`, кавычки и обратные слеши сохраняются как введены. Поэтому в .env.server значения записывают без добавления обрамляющих кавычек. Этот файл не следует выполнять командой `source`. Compose получает только домен из deploy/server-domain.env; секреты не используются для подстановки в YAML. [Описание raw в Compose](https://docs.docker.com/reference/compose-file/services/#format).

## Как выполняется проверка

Скрипт проверяет синтаксис домена и его разрешение через DNS, доступность Docker, версию Compose и занятость портов. Он не останавливает чужие веб-серверы. Настройки записываются после проверки ввода и совпадения паролей.

Далее скрипт проверяет конфигурацию Compose, запускает серверный проект и ожидает готовности приложения. Проверка HTTPS использует настоящий сертификат и доменное имя, но подключается к собственному серверу по 127.0.0.1. Проверка сертификата не отключается.

Успех означает, что приложение ответило через собственный HTTPS-прокси на этом сервере. Доступность сайта из сети сотрудника нужно проверить отдельно в браузере. Ключ ProxyAPI не тестируется платным запросом установщика: после входа задайте известный вопрос и вопрос без ответа, проверьте цитаты, историю, аудит и экспорт.

При ошибке установка завершается с ненулевым кодом. Созданные настройки, контейнеры и данные сохраняются для диагностики и повторного запуска; автоматического удаления данных нет.

## Справочная установка вручную

Основной способ — install.sh. Ручные действия ниже предназначены для администратора, которому нужна собственная настройка.

1. В папке проекта создайте .env.server из .env.example, если файла ещё нет:

   ```bash
   test -f .env.server || cp .env.example .env.server
   chmod 600 .env.server
   ```

2. В .env.server задайте PROXYAPI_API_KEY, ADMIN_PASSWORD, SESSION_COOKIE_SECURE=true и добавьте ATLAS_DOMAIN=ваш.домен. Значения вводятся буквально, без обрамляющих кавычек.
3. Создайте deploy/server-domain.env с единственной строкой `ATLAS_DOMAIN=ваш.домен`. Домен должен совпадать с .env.server. В этот файл не помещайте ключ или пароль.
4. Проверьте и запустите серверную конфигурацию:

   ```bash
   docker compose --env-file deploy/server-domain.env -f compose.server.yaml -p zag-atlas-server config --quiet
   docker compose --env-file deploy/server-domain.env -f compose.server.yaml -p zag-atlas-server up -d --build --wait --wait-timeout 180
   ```

5. Проверьте HTTPS-адрес и работу приложения. Сертификат настраивает Caddy по домену; дополнительные действия по выдаче/продлению в штатном сценарии не требуются. [Условия автоматического HTTPS](https://caddyserver.com/docs/automatic-https).

Наружу опубликованы только порты Caddy. Порты приложения и Qdrant не опубликованы на хост. Приложение доверяет заголовкам прокси внутри этого серверного профиля; Caddy передаёт исходный Host и сведения о клиенте. Не публикуйте atlas:8000 напрямую при этой настройке доверия.

## Состояние, логи и остановка

Все команды выполняются в папке проекта на сервере:

```bash
docker compose --env-file deploy/server-domain.env -f compose.server.yaml -p zag-atlas-server ps
docker compose --env-file deploy/server-domain.env -f compose.server.yaml -p zag-atlas-server logs --tail 100 atlas caddy
docker compose --env-file deploy/server-domain.env -f compose.server.yaml -p zag-atlas-server down
```

Обычный down сохраняет именованные тома. Организуйте резервное копирование и проверку восстановления данных приложения, Qdrant и сертификатов. Контейнеры и тома локальной учебной установки имеют другое имя проекта и этими командами не управляются.

## Если что-то не получилось

### Восстановление пароля admin

Владелец сервера может восстановить доступ без действующего пароля Atlas. Работайте в папке проекта через интерактивный терминал; на время процедуры приложение останавливается.

Сначала убедитесь, что образ содержит актуальную команду:

```bash
docker compose --env-file deploy/server-domain.env -f compose.server.yaml -p zag-atlas-server build atlas
```

После успешной сборки выполните по порядку:

```bash
docker compose --env-file deploy/server-domain.env -f compose.server.yaml -p zag-atlas-server stop atlas
docker compose --env-file deploy/server-domain.env -f compose.server.yaml -p zag-atlas-server run --rm --no-deps atlas python -m app.recover_admin
docker compose --env-file deploy/server-domain.env -f compose.server.yaml -p zag-atlas-server start atlas
```

Введите новый временный пароль дважды скрытым вводом. После завершения или отмены обязательно выполните start atlas. Если stop завершился ошибкой, сначала устраните её причину. Затем войдите через HTTPS и смените временный пароль на другой постоянный.

Старые сессии admin отзываются; другие сотрудники и знания сохраняются. Запись `CLI admin_password_recovery` доступна в аудите после отключения фильтра «Только вопросы». В .env.server пароль менять не требуется. Команда не принимает пароль аргументом или из перенаправленного stdin. Проверка этой процедуры на настоящем VPS ещё не выполнялась; локальные проверки приведены в [отчёте](../verification/ADMIN_RECOVERY_RESULTS.md).

### Диагностика

| Сообщение или симптом | Действие |
|---|---|
| Нельзя подключиться к Docker | Проверьте Docker Engine и разрешения серверной учётной записи |
| Порты заняты | Согласуйте с администратором размещение существующего веб-сервера; скрипт его не выключает |
| Домен не найден | Проверьте DNS, включая опечатки и Punycode |
| HTTPS не подтверждён | Проверьте A/AAAA, доступ к портам извне и логи caddy |
| Сайт работает, но ответ отмечен технической ошибкой | Проверьте ключ/доступность ProxyAPI и причину в аудите; сертификат и модель — разные проверки |
| Домен в двух файлах отличается | Согласуйте ATLAS_DOMAIN в .env.server и deploy/server-domain.env |

При передаче диагностики исключайте ключи, пароли и содержимое файлов секретов. Сам установщик не выводит их и не использует команды, печатающие полную конфигурацию с окружением.
